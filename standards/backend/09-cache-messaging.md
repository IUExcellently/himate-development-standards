# Redis、Kafka 与 XXL-Job

仅对实际使用对应组件的模块生效。依据 Redis、Kafka、Spring Kafka 与现有调度组件，见 [E08](../../references/coding-evidence.md)。

- MID-01 MUST。Redis key 保持模块前缀、租户隔离、版本与 TTL；以实际一致性要求设计写后失效和竞态。缓存穿透、击穿、雪崩按负载选择空值限期、并发合并、TTL 随机化与回源限流。审查序列化兼容、热/大 key、超时和有界重试。锁采用现有设施并核实所有者、租约、释放与过期后的副作用保护。
- MID-02 MUST。Kafka 核对 topic、partition key、群组、producer 确认、offset 提交、顺序和 schema 向后兼容。同 partition 的顺序还需考虑重试、并发或旁路。消费者按业务幂等键去重，明确处理成功/失败何时提交；重试与死信有可追溯的界限及回放授权。
- MID-03 MUST。Kafka 事务与 PostgreSQL 提交具备不同原子边界。为跨边界副作用核对现有幂等、补偿、可重放状态或业务持久机制。反例是以数据库 `@Transactional` 作为消息原子性依据；引入新中间件或持久机制要做范围/依赖审批。
- MID-04 SHOULD。XXL-Job 按实际执行器配置验证重复触发、分片、锁、并发限制、超时、批量游标、重试、告警、恢复与停机。使用可持久的业务进度和可重试幂等批次；区分调度成功和业务副作用完成。缓存或消息技术变更只作用于确有相关配置的模块。
